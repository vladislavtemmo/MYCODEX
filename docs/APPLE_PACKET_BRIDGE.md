# MYCODEX 8.3B2A — ограниченная двусторонняя очередь IP-пакетов

Дата: 2026-11-15. Основа: `feat/apple-core-integration` после `60685cd`.

## Реализовано

- `MYCODEXPacketBridge.cpp`: C++20 очередь `system→Core` / `Core→system`.
- В каждой очереди задано отдельное ограничение по числу пакетов и объёму памяти; по умолчанию 64 пакета и 1 МиБ на направление.
- C ABI `mycodex_packet_bridge_{create,push,pop,stats,close,destroy}`.
- `Sources/MYCODEX/MYCODEXPacketBridge.swift`: Swift-first оболочка с результатом `false` при переполнении без молчаливого удаления пакета.
- Очередь защищена mutex; IP-пакет копируется в очередь один раз, на выходе — в буфер владельца.
- Максимальная длина пакета — 65535 байт; IPv4 и IPv6 отделяются по версии IP.

## Критические ограничения

1. Это **пакетная staging-очередь**, а не TUN-адаптер и не работающий VPN. Пока не подключены ни `NEPacketTunnelFlow`, ни `TunBuilderBase`, ни C++ Core packet callbacks.
2. Не ставить `MYCODEX_HAS_APPLE_TUN_ADAPTER` и не снимать запрет `start()` до реальной интеграции. Windows и SwiftPM fallback по-прежнему должны собираться.
3. Возвращаемое `false` означает backpressure: владелец исходного пакета должен повторить передачу позже, а не потерять данные. Попытка использовать callback `packetFlow.readPackets` без учёта backpressure приведёт к потере IP-пакетов.
4. `close()` запрещает новые пакеты, но позволяет прочитать уже поставленные в очередь. `destroy()` должен происходить только после завершения всех операций; проверку гонок дополнить при интеграции `NEPacketTunnelProvider`.
5. `MYCODEXPacket` валидирует только минимальные свойства заголовка, не криптографию и не контрольные суммы. Пакеты из небезопасного источника дополнительно проверять в Core.
6. Динамическая память на пакет в текущем варианте используется: оптимизацию copy/alloc, батчинг и базовые показатели производительности провести после работающего end-to-end тракта.
7. Двусторонняя очередь не содержит специальной защиты от длительного зависания производителя. В реальном цикле пакетного потока потребуется асинхронное пробуждение/сигнализация, без активного poll-loop.

## Тестирование

`swift test`, `swift build -c release` — переносимые тесты пакетной очереди без Core. `bash scripts/test-macos-packet-bridge.sh` — регрессия ранее построенной интеграции и дополнительный Swift → C ABI → native .dylib пробник.

## Следующий шаг

Согласовать интерфейс между `NEPacketTunnelFlow` и native queue, затем реализовать `TunBuilderBase`/socketpair и последовательность `setTunnelNetworkSettings` с подтверждением Apple до сетевого запуска. Только подписанный Packet Tunnel Provider с реальным обменом пакетами даст право включить `start()`.
