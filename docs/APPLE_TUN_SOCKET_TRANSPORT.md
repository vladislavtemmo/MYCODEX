# MYCODEX 8.3B2D2B — POSIX datagram transport до интеграции с Core

Дата: 2026-11-15. База: `feat/apple-core-integration@b99979a`.

## Реализовано

- `MYCODEXTunSocketTransport.cpp` создаёт `socketpair(AF_UNIX, SOCK_DGRAM)` — две связанные стороны с сохранением границ IP-пакетов. На Windows функции возвращают явный отказ: POSIX-transport не применяется к Windows.
- Swift `MYCODEXTunSocketTransport` владеет нативным транспортом и удерживает `MYCODEXPacketBridge`, чтобы избежать освобождения очереди раньше транспорта.
- `duplicateCoreFileDescriptor()` возвращает *дубликат*, которым владеет и который закрывает вызывающая сторона. Дескриптор не подключается к OpenVPN автоматически.
- `pump(maxPerDirection:)` двигает пакеты между `.toCore` и fd, а также между fd и `.toSystem`. Цикл неблокирующий, ограниченный числом пакетов, возвращает количество переданных пакетов.
- При заполнении очереди `.toSystem` принятый из сокета пакет удерживается для повторной попытки. При временной невозможности `send()` пакет `.toCore` тоже сохраняется. Ничего не выбрасывается молча по причине переполнения очереди.
- `close()` идемпотентен; `destroy()` закрывает принадлежащие транспорту дескрипторы. Сырые пакеты не записываются в логи.
- Новые XCTest проверяют двусторонний пакетный путь, retry при переполнении, ошибочный пакет и закрытие. macOS native probe проверяет аналогичный путь вместе с реальной `libmycodex_core.dylib`.

## Ограничения и риски

1. **Это ещё не рабочий TUN**. `tun_builder_establish()` по-прежнему возвращает `-1`; `mycodex_client_start()` возвращает `-6`. Никакая VPN-сессия или событие `CONNECTED` не имитируется.
2. `socketpair` не связан с экземпляром OpenVPN Core — нативный тест имитирует Core-продюсера/потребителя с помощью дубликата fd. Следующий этап: выдача fd из `tun_builder_establish()` после подтверждения Apple `setTunnelNetworkSettings`, запуск worker-помпы, связь с `NEPacketTunnelFlow`.
3. `pump()` не включает вечный цикл/таймер — требуется реальное событие пробуждения или диспетчеризация readiness (`kqueue`/`DispatchSource`) для запуска без busy-wait и для немедленного возобновления после draining очереди.
4. `MYCODEXTunSocketTransport` и `MYCODEXPacketBridge` **не Sendable**: владелец обязан сериализовать операции, особенно закрытие/destruction с другими native вызовами. Ядро на своём fd может работать одновременно, но не должно обращаться к уже закрытому дескриптору после teardown.
5. Пакеты передаются через системный сокет и копируются в staging queue, поэтому пропускная способность и задержка могут быть ограничены. На устройстве понадобятся нагрузочные тесты и оценка памяти.
6. В этом этапе буферы сокетов увеличиваются по возможности, но конкретный предел буфера определяется ОС. Избыточный пакет может вызвать системную ошибку и не интерпретируется как успешная доставка.
7. Отказ IP-validity явный, но текущая проверка заголовка минимальная. Некорректные пакеты вызывают ошибку, а не скрытую корректировку.
8. `SOCK_DGRAM` сохраняет границы пакетов; нельзя заменять его на `SOCK_STREAM` без собственного length-framing и тестирования.

```bash
swift test
swift build -c release
bash scripts/test-macos-tun-socket.sh
```

Ожидаемый маркер `=== MYCODEX STEP 8.3B2D2B VERIFIED ===` подтверждает сборку Core и тест socketpair, но не реальный VPN.
